## Overview

The **Deterministic Multimodal Food Intelligence System** accepts a food image, a text query, or both. For image input, a vision model identifies the food and returns a food-name string. The application then embeds the resulting query with `sentence-transformers/all-MiniLM-L6-v2` and requests the single best match from a Pinecone index. The answer is assembled from the metadata attached to that vector record.

The intended nutrition source is a structured JSON dataset (`FoodDataSet.json`). At query time, however, the checked-in application reads the matching record's metadata from Pinecone; the script does **not** load or ingest the JSON file itself. The Pinecone index must therefore be populated from the intended dataset before using the app.

This separation is deliberate: language and vision models identify the query, while the displayed nutrition fields come from retrieved metadata rather than being generated by an LLM.

### What it supports

- Food identification from an uploaded image.
- Text-only nutrition lookup.
- Combined image and text queries, such as an image plus “calories”.
- Semantic retrieval using a fixed 384-dimensional embedding model.
- Single-result retrieval (`top_k=1`) through Pinecone.
- Display of food name, calories per serving, cuisine, description, and vector similarity score.
- A lightweight Gradio interface for trying the different input paths.

## Design goals

### Structured, dataset-grounded answers

The application returns fields from the selected Pinecone record's metadata. It does not ask a generative model to invent calorie or nutrition values. The integrity of those values depends on the quality and provenance of the dataset used to populate the index.

### Fixed retrieval configuration

The current implementation uses one embedding model, normalized embeddings, a fixed 384-dimensional vector space, and a top-1 Pinecone query. It does not use a reranker or combine several retrieved results.

### Small, inspectable pipeline

The main request path can be traced from user input through food identification (when an image is supplied), embedding, vector lookup, and formatting of the retrieved metadata. The application is intended as a transparent engineering demonstration rather than a general-purpose nutrition assistant.

> **Terminology note:** “Deterministic” describes the fixed retrieval configuration and metadata-grounded response construction. The complete system is not guaranteed to be bit-for-bit deterministic: image identification uses a hosted vision model, and retrieval is performed by a managed vector database.

## How it works

1. **Input:** The user uploads an image, enters text, or supplies both.
2. **Food identification (image path):** The image is sent to OpenAI's `gpt-4.1-mini` with an instruction to return only the food name.
3. **Query assembly:** The returned food name is combined with optional user text.
4. **Embedding:** The query is encoded by `sentence-transformers/all-MiniLM-L6-v2` into a normalized 384-dimensional vector.
5. **Vector retrieval:** Pinecone is queried with `top_k=1` and metadata included.
6. **Response formatting:** The app formats the selected record's metadata into a readable response and shows the Pinecone similarity score.
7. **No match:** If Pinecone returns no match, the interface displays a no-match message rather than generating a nutrition answer.

## Architecture

```text
                  User Input

               │             │

               │             │

      OpenAI GPT-4.1-mini    │
      Food-name extraction  │
               │             │
               └──────┬──────┘

                Query assembly
                      │
                      ▼
       all-MiniLM-L6-v2 sentence embedding
             normalized, 384 dimensions
                      │

                      │
                      ▼
          Retrieved record metadata
      food_name | calories | cuisine | description
```

The vision stage is used only when an image is supplied. Text-only requests go directly to query embedding and retrieval.

## Retrieval and data contract

### Embedding configuration

| Setting | Value |
|---|---|
| Model | `sentence-transformers/all-MiniLM-L6-v2` |
| Vector dimension | `384` |
| Normalization | Enabled (`normalize_embeddings=True`) |
| Vector database | Pinecone |
| Index name | `food-rag-index` |
| Result count | `top_k=1` |
| Reranking | None |

The Pinecone index must be configured for **384-dimensional vectors** and a metric compatible with normalized embeddings, such as cosine similarity or dot product. The application expects the index to contain usable food records and metadata.

### Expected metadata fields

The response formatter reads these fields from the selected match:

| Field | Purpose | Behavior if missing |
|---|---|---|
| `food_name` | Matched food label | Displays `N/A` |
| `calories` | Calories per serving | Displays `N/A` |
| `cuisine` | Cuisine label | Displays `N/A` |
| `description` | Food description | Displays `N/A` |

The Pinecone similarity score is displayed separately. A top-1 result is the best match returned by the configured index, not proof that the identified food is correct. A low-quality match can still be returned when the index contains related but non-equivalent records.

### Dataset provenance

The intended source dataset is named `FoodDataSet.json`, but that file is not present in the current project-directory listing. The application code does not load the JSON file or synchronize it to Pinecone. You must populate `food-rag-index` from your trusted dataset separately and ensure the indexed metadata follows the schema above. Do not assume the data is present simply because the interface can connect to Pinecone.

## Requirements and configuration

The checked-in script was exported from Google Colab and contains notebook-specific syntax (`!pip install`) plus `google.colab.userdata`. As currently committed, it is **not a plain standalone Python script** that can be run unchanged with `python deterministic_multimodal_food_intelligence_system.py` in a regular terminal. The steps below describe the intended Colab workflow.

Required packages:

```bash
pip install gradio sentence-transformers pinecone-client openai pillow
```

You also need:

- An OpenAI API key with access to `gpt-4.1-mini` for image-based identification.
- A Pinecone API key.
- A Pinecone index named `food-rag-index`, configured for 384-dimensional vectors and populated with food records.
- Colab Secrets named `OPENAI_API_KEY` and `PINECONE_API_KEY`.

The credentials are read in the code through:

```python
OPENAI_API_KEY = userdata.get("OPENAI_API_KEY")
PINECONE_API_KEY = userdata.get("PINECONE_API_KEY")
```

Never commit API keys to the repository or paste them into source code.

## Run in Google Colab

1. Open a new notebook in [Google Colab](https://colab.research.google.com/).
2. Add `OPENAI_API_KEY` and `PINECONE_API_KEY` to the notebook's Secrets panel. Grant the notebook access to both secrets.
3. Confirm that the Pinecone index `food-rag-index` exists, has dimension `384`, and contains the expected food metadata. Prepare/populate the index separately from the app if required.
4. Copy the application source into a notebook code cell, preserving the initial `!pip install` command, or convert the script to a notebook cell before running it. The current `.py` export contains Colab-only syntax.
5. Execute the cell. The script initializes the embedding model and Pinecone client, then launches the Gradio interface.
6. Use the generated Gradio link to test image-only, text-only, and combined inputs.

For use outside Colab, first replace `google.colab.userdata` with an appropriate environment-variable or secrets manager, move package installation out of the source file, and expose the entry point through a standard Python module. That adaptation is not included in the current repository snapshot.

## Expected behavior

- **Image provided:** identify a food name with the vision model, append optional text, then query Pinecone.
- **Text only:** embed the text and query Pinecone directly.
- **Image and text:** combine the recognized food name with the user's text before retrieval.
- **Empty input:** display an instruction to upload an image or enter text.
- **No Pinecone match:** display `No match found in FoodDataSet.json`.
- **Incomplete metadata:** display `N/A` for the missing fields.
- **Service or configuration error:** the Gradio handler returns an error string. Check API credentials, Pinecone index configuration, network access, and package compatibility.

## Limitations and implementation notes

- **Dataset coverage:** The system can only return records already available in the Pinecone index. Unknown foods or missing entries may yield no result or an incorrect nearest match.
- **Vision uncertainty:** Food identification is produced by a hosted model and may be incorrect, particularly for mixed dishes, obscured food, similar-looking dishes, or poor-quality images.
- **Top-1 retrieval only:** No confidence threshold, multi-result display, or reranker is implemented. The highest-ranked result may not be an exact match.
- **Nutrition accuracy:** The app reports indexed metadata; it does not independently validate serving size, nutrition facts, or dataset provenance.
- **No nutrition estimation:** It should not infer values for foods absent from the index.
- **External services:** Image-based queries send the uploaded image to OpenAI. All queries requiring retrieval use Pinecone. These requests depend on provider availability and applicable data-handling terms.
- **Current execution format:** The source contains Colab-specific syntax and secret access. Direct terminal execution requires adaptation.
- **Dataset loading:** The app does not ingest `FoodDataSet.json`; index creation and dataset synchronization must be handled separately.
- **No medical use:** Results are for software demonstration and general information, not for clinical, allergy, medication, or therapeutic decisions.

## Security and privacy

- Store API keys in Colab Secrets or an equivalent secrets manager.
- Do not commit keys, provider tokens, or private datasets.
- Images submitted through the image path are sent to the OpenAI API for identification.
- Text queries and their generated embeddings are sent to Pinecone for retrieval.
- Review OpenAI and Pinecone data-handling terms before using personal, confidential, or regulated data.
- Restrict access to any deployed Gradio interface; the current demo does not implement user authentication.
